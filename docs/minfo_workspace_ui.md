# minfo 工作区 UI

插件 2.0 以一次 `.minfo` 导入创建的 Collection 作为独立编辑会话。Collection 保存用户选择的 minfo 路径、`workspace.json`、模型根对象、Armature 和主 Mesh 指针；Cloth、SOP 与 MOT 状态继续保存在该会话的 Armature 上。导入多个 minfo 时，各集合的材质、约束、动画缓存、Cloth 参数和构建目标互不共享。

3D 视图右侧 `GBFR > GBFR 工作区` 是中控面板。顶部菜单切换会话并选中其 Armature，路径栏显示当前编辑的 minfo 源地址。选择某个已导入对象时，面板自动使用该对象所属会话；选择用户在其他 Collection 中导入的替换模型时，中控仍保持显式选择的 GBFR 会话，不会把插件操作应用到替换模型。

中控操作：

- 导入按钮创建新的 minfo 会话，不覆盖现有会话。
- “恢复”重新读取当前会话的材质、Cloth XML、SOP 和 MOT 列表，会丢弃这些中间态的当前编辑；它不会重新创建 Mesh 或 Armature。
- “导出到工作区”先锁定当前会话根对象，再让用户选择 `workspace.json`。文件选择器会在确认前列出模型 ID，以及将覆盖的 `.minfo`、`.skeleton` 和全部 `lod#`/`shadowlod#` `.mmesh` 路径，并明确提示不会写入 `build`。插件复制当前会话的完整层级到临时场景，由 v2 构建器直接生成二进制并原子覆盖 `unpack`，同时把当前全部 CLP/CLH 写入目标 workspace 登记的 `unpack` XML；不使用其他 Collection 中的活动对象，也不生成 `_Exported_MInfo`、BXM 或中间 JSON。
- 打开导出文件选择器时会自动检查当前会话全部导出 Mesh 的顶点权重，界面也提供“重新检查”。正权重总和与 1 的误差超过 `1e-6`（包括完全无权重）记为未归一化；正权重 influence 超过 4 个单独记为超限。两类问题按 Mesh 显示红色数量警告，但不会替用户修改权重或强制取消实验性导出。“限制为 4/8 权重”会在操作完成后自动重新检查并刷新该警告；手工编辑权重后仍应点击“重新检查”。
- 同一个 `.blend` 可以同时保留身体和头部等多个 minfo 会话，也允许把当前会话显式导出到另一份含相同模型 ID 的 workspace。插件负责在确认前展示实际目标并验证目标模型契约，但不会假定目标必须等于导入时的 workspace；目标工作区的选择与后续投放由用户负责。MOT 逐行动画导出仍绑定动画所属会话的 workspace，不跟随模型导出文件选择器临时改向。
- “对象”面板只选择或控制当前会话记录的模型根对象、Armature、主 Mesh 与 Collection；材质摘要会统计全部 LOD 下的 Mesh。
- “材质”“Cloth”“SOP 约束”“MOT 动画”都是中控子面板，只解析当前会话。

旧版 Fixes、Utilities、Materials、Advanced 和 Credits 已汇总为同一 `GBFR` N 栏标签下的顶级“GBFR 实用工具”面板。它不是工作区中控的子面板，内部按骨架、网格、材质 ID、高级和项目链接折叠；骨骼名称可在 GBFR 编号与 Unity/Blender 人形名称之间双向转换，旧的网格清理、拆分/合并、材质 ID 与 minfo Magic 操作也保留。该面板明确作用于 Blender 当前活动对象，方便处理用户自己导入的替换模型；它不会因为中控选中了某个 minfo 会话而自动改动会话对象。

面部 `_8xx` 权重骨在转为 Unity/Blender 名称时使用 Blender 可镜像的 `.L/.R` 后缀。已确认区域使用 `BrowInner.L`、`UpperEyelid.L`、`EyeContour01.L`、`EyeBall.L`、`EyeSocket.L`、`Ear.L`、`MouthCorner.L`、`UpperLip01.L`、`LowerLip01.L` 等语义名称；中线使用 `NoseBridge01`、`UpperLipCenter`、`LowerLipCenter`、`UpperTeeth`、`LowerTeeth` 和 `TongueTip`。尚未确认的骨继续使用 `FaceDeformXX.L/.R` 或无后缀的 `FaceDeformXX`。左右配对来自 `fp1400` 静止位置与权重质心的镜像验证；没有可靠左右依据且不参与当前网格权重的 `_8a4/_8a5/_8a7/_8a8/_8d0` 不伪造侧别。转回 GBFR 时优先读取骨骼保存的 `gbfr_original_name`/`gbfr_bone_id`，因此骨名、顶点组和 MOT Action 曲线路径可以无损恢复；generic FaceDeform 与旧 Eye/Brow/Lip 名称均保留为反向转换兼容别名。

模型导出只写入工作区中已登记的 `unpack` 二进制，不会直接写入 `build`。在 GBFR Modtools 预览、刷新并确认后，再由编辑器复制到 `build`。`flatc.exe` 不再参与模型导出；它仍可能被 Modtools 的其他格式工具使用。

## 融合骨架与稳定索引

Blender 的 `Armature.data.bones` 顺序不是可靠的游戏骨骼索引。即使融合工具只是使用 `edit_bones.new()` 添加骨骼，新骨挂到已有父骨并退出编辑模式后，Blender 也可能按层级把新骨插入旧骨序列中间。父子关系仍然正确，但如果直接按该集合顺序写 `.skeleton`，原来的 cloth、SOP、动作和顶点权重会指向错误骨骼，游戏可能在载入模型时崩溃。

工作区导出不再依赖 Blender 的内部顺序。存在 source `.skeleton` 时，导出器按导出骨名匹配并建立一张稳定索引表：

1. source 中的全部原骨骼保持原索引和原顺序。
2. 融合后新增的骨骼统一追加到 source 骨骼之后。
3. `.skeleton` 的 `ParentId`、`.minfo` 的 deform bone 表和 `.mmesh` 权重索引共同使用这张表。

source `.skeleton` 只提供稳定索引契约，不会替代当前 Blender 的 rest pose。导出器对 Blender 中存在的每根原骨重新读取 `bone.matrix_local`，写出当前局部位置和旋转；因此移动脸骨的 `head`、改变方向或 Roll 会进入新的 `.skeleton`。单纯沿原方向修改 `tail` 长度不会改变矩阵，也不会写出骨长。`fpXXXX` 已知存在 Blender 导入时因近零缩放而省略的非蒙皮占位骨（例如 `_8d0`）；这些缺失槽位单独从 source 原样保留，其他脸骨仍按 Blender 当前变换重建，不能再通过复制整份 source skeleton 处理。

头部 `fpXXXX` 和身体 `plXXXX` 虽然分别导出，游戏运行时仍会按导出骨名合并两套骨架。两边 source 原本就有的同名骨是有意共享，必须保持；风险只在两边各自新增骨时出现。自动编号器只看当前导出会话的 source、Cloth 保留引用和当前骨架，不会读取另一个头部或身体会话已经给新增骨分配了什么名称，因此两边可能独立得到同一个 `_cxx/_axx/_dxx/_xxx`。相同的追加数组下标本身没有关系，真正冲突的是相同的四字符导出骨名。当前推荐只在身体骨架增加新骨，头部只编辑 source 已有脸骨；如果确实需要两边都新增，必须先显式固定互不重叠的合法四字符骨号，并在两个导出的 `.skeleton` 间核对新增名称，当前插件不会替用户完成跨会话分配。

父子关系通过重新计算的 `ParentId` 保持，不要求父子骨在 Blender 列表中相邻。当前回归样本已验证：342 根原骨融合为 838 根后，原骨名称和父索引逐项不变，新增骨从索引 342 开始输出。

这项处理属于 GBFR 导出契约，不要求通用骨架融合工具写入 GBFR 自定义属性。已经融合好的 `.blend` 也可直接根据工作区 source skeleton 恢复导出顺序。前提是原骨骼没有被删除、重命名或改变父级；除 `fpXXXX` 已知非蒙皮占位槽外，缺少源骨、出现重复导出骨名或修改原父级时，导出器会拒绝生成不一致的文件。

重新导出后必须把同一次生成的 `.minfo`、`.skeleton` 和全部 `.mmesh` 一起构建、投放。只替换 `data/model_streaming` 中的 `.mmesh`，让它搭配游戏原版 `.minfo/.skeleton`，会造成权重表和骨骼索引契约不一致。

## 顶点权重量化的强制契约

每个蒙皮顶点写入 `.mmesh` 的权重是四个或八个 `uint16`，精度为 `1/65535`。游戏的角色顶点着色器直接用这些权重线性混合三行、每行四个分量的骨矩阵，不会在蒙皮前后除以权重总和。矩阵的平移分量也参与混合，因此每个顶点的整数权重和必须严格等于 `65535`，不是“大约等于 1”即可。

旧导出器虽然先在 Blender 中执行浮点归一化，却对每个分量独立执行 `round(weight * 65535)`。独立舍入不能保持整数总和：实测旧 `pl1400` 导出物的 49,011 个顶点中，2,519 个合计为 `65534`，2,395 个合计为 `65536`；裙子 3,896 个相关顶点中有 535 个欠 1、581 个多 1。官方 source 的四个 LOD 则每个顶点都严格等于 `65535`，没有例外。

这个一单位误差不能当作无害精度噪声。角色顶点着色器会把欠 1 的顶点按 `1/65535` 的比例漏掉骨矩阵中的世界平移，使其沿角色到世界原点的方向偏移；多 1 的顶点则反向偏移。角色离世界原点越远，误差越明显，并会在平整裙面、袖面和前发上形成随机毛躁或扭曲。插件预览 shader 曾对蒙皮位置除以 `weightSum`，所以会掩盖磁盘文件中的这个错误，不能用预览平整证明游戏输入安全。

导出器现在统一量化一个顶点的全部有效权重：保留已经位于 `1±1e-6` 内的 Blender 归一化值，只对真正未归一化的输入重新归一化；随后逐分量四舍五入，并把与 `65535` 的整数差值补到权重最大的主 influence。该方法保持原有 16 位精度与次要权重的独立舍入结果，同时保证最终整数和严格为 `65535`；容差和整数主权重补偿也避免重复 LOD 之间几 ULP 的浮点差异改变最终字节。没有任何正权重的顶点会直接阻止导出，不再静默写出会坍向原点的零和数据。

此修复会改变旧文件中所有 `65534/65536` 顶点的权重字节及 `.mmesh` 哈希。已经生成的 `unpack` 和 `build` 不会自动修复；必须使用更新后的插件重新导出，并重新构建、投放同一模型的全部 LOD。不得只修单个可见部件或手工修改少量异常顶点，因为误差分布在整个共享权重缓冲中。
