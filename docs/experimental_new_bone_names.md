# 实验性新增骨骼命名

在工作区导出面板勾选“实验：新增骨骼使用白名单编号”后，导出器只会在临时导出副本中处理新增骨骼：

- 参考 skeleton 中已有的骨骼保持原名称、原索引和原顺序；新增骨骼仍追加在末尾。
- source skeleton 中已有的名称、索引和顺序具有最高优先级，包含 PL/FP 原本就会共享的骨骼；自动编号只处理相对当前 source 新增的骨骼。
- 新增骨如果由用户直接命名为合法的四字符骨号，会视为显式固定编号；但显式编号仍不能占用已确认的 FP 面骨号。
- 普通用户骨名上的 `gbfr_bone_id` 是模型与 Cloth 对接使用的隐藏导出编号，不等于用户改名。旧版本留下且没有当前策略版本标记的隐藏编号会在下一次联合导出时重新分配一次；新策略产生的编号随后保持稳定，避免每次导出漂移。
- CLP/CLH 中仍存在但没有对应真实骨对象的原始编号先进入保留集合，自动分配不得占用；有真实骨对象的引用会随该骨的新编号一起迁移。
- 新增骨名称按 `_c00`～`_cff`、`_a00`～`_aff`、`_d00`～`_dff`、纯数字 `_000`～`_999` 的顺序分配；每个候选都会跳过参考骨架和当前导出副本已经占用的名称。
- `FACE_DEFORM_GROUPS` 中已经确认的 FP 面骨号是全局保留项。单独导出 PL 时也不会把新增骨分配为 `_830`、`_880`、`_890` 等面骨号。
- 对应 mesh 的 Blender 顶点组会同步改名，权重数据不变。
- 骨骼对象的 `parent` 指针、位置、姿态和层级不改；原始 Blender 场景不会被重命名。

## 当前编号规律

预览器按十六进制解析骨名 `_xxx`，因此名称是三位十六进制骨骼 ID；首位字符同时表现出功能分区，而不是 skeleton 数组下标：

- `_000`～`_015` 等数字区是身体主骨；纯数字 `_000`～`_999` 只作为最后的容量补充，并始终排除已确认的 FP 面骨号。
- `_axx` 主要是 Deform/Twist/Corrective 骨，许多目标由 `.sop` 在动画之后驱动；新增骨不应覆盖已有 `_aXX` 或 SOP 引用。
- `_cxx` 是角色布料/动态辅助骨常见的分区，`pl1400` 的 `.clp/.clh` 已引用 `_c45`～`_c65`；本实验允许使用空闲 `_cXX`，但不会自动生成 cloth 配置。
- `_dxx` 在当前角色中属于未完全解码的辅助分区，只作为低优先级实验候选。
- 联合导出界面的 CLP 主骨污染警告只检查本次新增且落入纯数字 `_000`～`_999` 区的骨骼；导入 source 时已有 `gbfr_original_index/gbfr_original_name` 标记的原始骨骼（包括 `_310`）不再仅因名称格式被误报。`_axx`、`_cxx`、`_dxx` 也不属于该警告范围。

## 已确认：PL/FP 合并时的跨骨架名称冲突

最终 Mod 中，PL 新增骨曾被临时编号为 `_830`、`_831`、`_880`、`_890` 等名称，而这些名称在 FP 中分别属于眉毛和嘴部面骨。游戏合并 PL 与 FP 骨架后，面部顶点会绑定到身体新增链，表现为不继承 Head、不响应脸部 MOT，并被拉向身体。数字区优先级本身不是矩阵分类问题，但会显著增加这种跨骨架碰撞；因此数字区已降为最后候选，并显式保留当前已确认的 FP 面骨号。

### 两边都新增骨时的剩余边界

`plXXXX` 与 `fpXXXX` 是两个独立工作区会话，导出时分别计算新增骨名称。自动分配器会排除当前 source、当前骨架、当前 Cloth 引用和已知 FP 面骨保留项，但不会读取另一个会话的新增骨分配结果。因此，即使身体侧已经避开所有官方 FP 面骨，若头部也新增骨，两边仍可能各自分配出同一个空闲名称，例如都得到 `_c06`；游戏合并时会按同名骨处理，位置、父级、权重或动画可能串到另一侧。

不要用两边 `.skeleton` 中的数组下标判断是否冲突。数组下标只服务各自文件内部的 deform 表和权重表；跨 PL/FP 合并需要比较四字符导出骨名。source 中原本就重叠的名称属于官方共享骨，不能为了“去重”而改名。当前安全工作流是：

1. 新增骨统一放在身体 `plXXXX`，头部 `fpXXXX` 只调整 source 已有脸骨的 rest transform、权重和 MOT。
2. 如果头部确实必须新增骨，为头部和身体新增骨分别指定合法且互不重叠的固定四字符骨号，不依赖两次独立自动分配。
3. 两边导出后比较 `.skeleton` 的新增名称集合；只允许 source 原本就存在的共享名称重叠，再进入 build 和游戏测试。

当前插件没有跨会话骨号注册表，也不会因为同一个 `.blend` 同时载入头、身体会话就自动协调编号。这是已知风险边界，不应把单个会话显示“无冲突”理解为最终合并一定无冲突。

对当前 `输出.blend` 的 `pl1400.004` 做只读预分配时，342 根 source 原骨保持不变，550 根新增骨分布为 `_cxx` 183 根、`_axx` 172 根、`_dxx` 145 根、纯数字区 50 根，和已确认 FP 面骨号的交集为 0。该数量只描述当前工程；其他模型的 source 占用和 Cloth 保留引用不同，实际分布也会不同，但优先级顺序不变。

## Blender Bone Collection 与 skeleton A1

Blender Armature 的 Bone Collection 不只是插件内的整理信息。当前导出器会把集合名编码为最多四字节 ASCII，并写入每根骨骼的 `Bone.A1.Unk`：

- source 导入的 `_0/_1/_2/_3/_4/_5/_9/_a/_c/_d` 集合来自原 skeleton，应保持原值。
- 用户自建的 `_h/_v/_s/Humanoid` 也会被导出；`Humanoid` 会被截断为 `_Hum`。这些值没有经过游戏契约验证。
- 同一骨骼属于多个集合时，当前实现最终使用集合遍历顺序中最后匹配的值；不属于任何集合时不会写 A1。

Bone Collection 与骨名白名单是两套独立字段。自建集合可能影响运行时骨骼分类，但 `pl1400.004` 的前发和后发都属于 `_h`，因此 A1 分组无法单独解释“前发毛躁、后发正常”的区域差异。上述命名优先级实验没有改变 A1，自定义 A1 是否影响运行时仍需作为独立变量验证，不能随骨名分区一起判定为已排除。

该白名单是基于当前角色和已验证资源的实验范围，不是官方完整的骨骼分配表。候选名仍需避开 `.skeleton`、`.sop`、`.clp/.clh`、动画和其他运行时配置中的已有引用。

这是用于验证游戏是否接受新增物理骨骼的实验开关，不负责为新增骨骼生成动画或 SOP/cloth 配置。
