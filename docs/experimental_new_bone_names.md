# 实验性新增骨骼命名

在工作区导出面板勾选“实验：新增骨骼使用白名单编号”后，导出器只会在临时导出副本中处理新增骨骼：

- 参考 skeleton 中已有的骨骼保持原名称、原索引和原顺序；新增骨骼仍追加在末尾。
- 名称白名单按优先级分为纯数字 `_000`～`_999`、`_c00`～`_cff`、`_a00`～`_aff`、`_d00`～`_dff`；每个候选都会跳过参考骨架和当前导出副本已经占用的名称。
- 对应 mesh 的 Blender 顶点组会同步改名，权重数据不变。
- 骨骼对象的 `parent` 指针、位置、姿态和层级不改；原始 Blender 场景不会被重命名。

## 当前编号规律

预览器按十六进制解析骨名 `_xxx`，因此名称是三位十六进制骨骼 ID；首位字符同时表现出功能分区，而不是 skeleton 数组下标：

- `_000`～`_015` 等数字区是身体主骨；本实验白名单把纯数字 `_000`～`_999` 放在最高优先级，已验证 `_016` 可用。
- `_axx` 主要是 Deform/Twist/Corrective 骨，许多目标由 `.sop` 在动画之后驱动；新增骨不应覆盖已有 `_aXX` 或 SOP 引用。
- `_cxx` 是角色布料/动态辅助骨常见的分区，`pl1400` 的 `.clp/.clh` 已引用 `_c45`～`_c65`；本实验允许使用空闲 `_cXX`，但不会自动生成 cloth 配置。
- `_dxx` 在当前角色中属于未完全解码的辅助分区，只作为低优先级实验候选。

## 已排除：命名分区优先级

曾将分配顺序临时改为 `_cxx → _dxx → _axx → 数字区` 并重新导出 `pl1400.004`。496 根新增骨实际分配为 `_cxx` 183 根、`_dxx` 145 根、`_axx` 168 根，数字区为 0 根；游戏内毛躁现象没有任何改善。因此可以排除“新增骨落入数字身体区，或不同骨名首字符分区触发特殊矩阵处理”这一原因。为避免保留一个没有收益的行为变化，分配顺序已恢复为原实验顺序。

## Blender Bone Collection 与 skeleton A1

Blender Armature 的 Bone Collection 不只是插件内的整理信息。当前导出器会把集合名编码为最多四字节 ASCII，并写入每根骨骼的 `Bone.A1.Unk`：

- source 导入的 `_0/_1/_2/_3/_4/_5/_9/_a/_c/_d` 集合来自原 skeleton，应保持原值。
- 用户自建的 `_h/_v/_s/Humanoid` 也会被导出；`Humanoid` 会被截断为 `_Hum`。这些值没有经过游戏契约验证。
- 同一骨骼属于多个集合时，当前实现最终使用集合遍历顺序中最后匹配的值；不属于任何集合时不会写 A1。

Bone Collection 与骨名白名单是两套独立字段。自建集合可能影响运行时骨骼分类，但 `pl1400.004` 的前发和后发都属于 `_h`，因此 A1 分组无法单独解释“前发毛躁、后发正常”的区域差异。上述命名优先级实验没有改变 A1，自定义 A1 是否影响运行时仍需作为独立变量验证，不能随骨名分区一起判定为已排除。

该白名单是基于当前角色和已验证资源的实验范围，不是官方完整的骨骼分配表。候选名仍需避开 `.skeleton`、`.sop`、`.clp/.clh`、动画和其他运行时配置中的已有引用。

这是用于验证游戏是否接受新增物理骨骼的实验开关，不负责为新增骨骼生成动画或 SOP/cloth 配置。
